# Database Schema — KotaLabs CRM

PostgreSQL 13+. Source of truth: `apps/backend/migrations/0001_init.sql`.
The migration runner (`npm run db:migrate`) applies files in filename order and
records them in `schema_migrations`.

## Conventions

- Primary keys are UUIDs (`gen_random_uuid()`), so offline-generated rows
  (Android) can be referenced without a round-trip.
- Human-readable numbers are separate: `leads.lead_number` (bigint identity)
  is displayed as `MMB-000001` in the UI and exports.
- Status-like columns are `text` + `CHECK` constraints, not native enums, so
  adding a value later is a cheap migration.
- All timestamps are `timestamptz` stored in UTC; the UI renders IST
  (Asia/Kolkata).
- Phone numbers are stored normalized to E.164 (`+919876543210`) and checked
  with `^\+[1-9][0-9]{6,14}$`. The API normalizes input with
  `libphonenumber-js` (default region `IN`).

## Tables

### `users`
Admin + employees. `role` ∈ {ADMIN, EMPLOYEE}, `status` ∈ {ACTIVE, DISABLED}.
`email` is unique (stored lowercase). `password_hash` is scrypt (Node stdlib),
format `scrypt$N$r$p$salt$hash`.

### `auth_refresh_tokens`
Rotating refresh tokens. Only the SHA-256 hash is stored. `revoked_at` marks
logout / rotation / password change. Reusing a revoked token revokes **all**
sessions of that user (theft detection).

### `devices`
One row per registered Android phone. `device_code` is the stable identifier
generated by the app, unique per user. Only the SHA-256 of the device token is
stored; the token is shown once at registration. `status` ∈ {ACTIVE, REVOKED}.

### `leads`
One row per customer enquiry (not per call).
- `source` ∈ {INSTAGRAM, YOUTUBE, GOOGLE_ADS, WHATSAPP, PHONE_CALL, WALK_IN,
  REFERRAL, MANUAL, OTHER}
- `status` ∈ {NEW, CONTACTED, INTERESTED, FOLLOW_UP, CONVERTED, LOST}
- `LOST` requires `lost_reason` (CHECK constraint).
- `platform_lead_id` + `source` are unique together (partial unique index), so
  a Meta/Google lead can never be imported twice.
- `next_followup_at` mirrors the earliest pending follow-up (kept in sync by
  the API) so dashboards don't need an aggregate query.
- `closed_at` is set when the lead becomes CONVERTED/LOST.

Duplicate rule (enforced by the API, not the DB): an **open** lead
(status NOT IN (CONVERTED, LOST)) for the same phone number blocks a new lead
with `409 DUPLICATE_LEAD`. Closed leads don't block a fresh enquiry.

### `call_events`
One row per individual call. `event_id` (client-generated UUID) is UNIQUE and
is the idempotency key for Android sync retries.
- `direction` ∈ {INCOMING, OUTGOING, MISSED, REJECTED, UNKNOWN} (nullable —
  unavailable fields stay NULL, never invented)
- `source` ∈ {SIM, WHATSAPP, MANUAL}
- `capture_method` ∈ {CALL_LOG, CALL_SCREENING, MANUAL}
- `duration_seconds`, `sim_slot` (1|2) nullable
- `lead_id` nullable: a call never creates a lead. When
  `CALL_EVENT_AUTO_LINK_LEAD=true`, the server links the most recent open lead
  with the same phone number.

### `lead_activities`
Append-only timeline: CREATED, NOTE, STATUS_CHANGE, ASSIGNMENT, CALL,
FOLLOWUP_SCHEDULED, FOLLOWUP_COMPLETED, FOLLOWUP_CANCELLED, UPDATED,
SOURCE_SYNC. `metadata` (jsonb) carries structured details.

### `followups`
Scheduled callbacks. `status` ∈ {PENDING, COMPLETED, CANCELLED, MISSED}.
COMPLETED requires `completed_at` (CHECK constraint).

### `webhook_events` (Stage 6)
Raw verified payloads from Meta / Google Ads. UNIQUE(provider, idempotency_key)
prevents duplicate imports; `status` ∈ {RECEIVED, PROCESSED, FAILED,
DUPLICATE, IGNORED} allows replay of failed imports.

### `audit_logs`
Who did what, for security review. `actor_type` ∈ {USER, DEVICE, SYSTEM,
WEBHOOK}.

## Key indexes

| Index | Purpose |
|---|---|
| `leads_open_phone_idx` | "open lead for this number?" during call matching |
| `leads_assigned_idx` | employee dashboard queries |
| `leads_next_followup_idx` | "due today / overdue" dashboards |
| `call_events_unmatched_idx` | calls with no lead (admin review) |
| `followups_pending_idx` | pending follow-up lists |
| `leads_source_platform_unique` | duplicate social-lead prevention |

## Adding a migration

1. Create `apps/backend/migrations/0002_<description>.sql` (next number).
2. Keep it transactional (the runner wraps each file in BEGIN/COMMIT).
3. Run `npm run db:migrate` and commit the file.
